# InkDOS 2.3 Design Specification

**Status:** USER-APPROVED — explicit user approval received 2026-09-12

**Target release:** `2.3.0`

## Purpose

This specification freezes the agreed InkDOS 2.3 product direction so later development runs do not silently reorder, simplify, reinterpret, or omit requirements. The four goals below must be implemented in the stated order. The web application remains local-first and independently usable; the installed desktop product extends the same workspace code through Tauri v2.

## Fixed execution order

1. Expand editable format coverage while preserving original formats where safe.
2. Fix PowerPoint/PPTX fidelity using evidence-based debugging and the real supplied regression.
3. Add installed-desktop integration: strict file associations, workspace-specific launch entries, and one native window per opened file while retaining one InkDOS installation.
4. Add the manual-only desktop updater and update shortcut, without redesigning Home.

## Global constraints

InkDOS remains local-first, offline-capable, client-side, without telemetry or a backend. Desktop remains Tauri v2; do not replace it with Electron or a bundled Node/Chromium stack. Documents, Spreadsheets, Presentations, PDF, Plain Text and EPUB remain independent workspaces and must not become application dependencies of each other.

Home remains a launcher/bridge. The web Home must not be redesigned. The desktop Home remains visually equivalent to web except for the approved manual-update control in Goal 4. Do not add a universal `Open file` card, central tabs, document lists, or cross-workspace router UI. Do not create six complete installations or duplicate full executables. Do not silently convert formats, silently reroute unsupported files, or discard unsupported data.

## Goal 1 — Expanded editable format coverage

### Plain Text

Plain Text remains a raw-text editor. Expand its current TXT/XML allowlist to:

- `.txt`
- `.xml`
- `.md`, `.markdown`
- `.json`, `.jsonl`, `.ndjson`
- `.yaml`, `.yml`
- `.log`
- `.ini`
- `.cfg`, `.conf`
- `.toml`
- `.properties`

Approved files remain editable and save back to the same filename/extension by default. YAML, JSON, Markdown, configuration files, etc. must not be converted to `.txt`. Preserve encoding, BOM and line endings as safely as the current text engine allows; retain XML-specific storage/encoding safeguards. Unsupported binary/office files sent to Plain Text must be rejected with a clear compatibility message rather than redirected.

### CSV/TSV

CSV and TSV belong to Spreadsheets because their user-facing semantics are tabular. They should open as cells, remain editable, and save back to `.csv`/`.tsv` by default. Do not convert them to XLSX merely because they were edited.

Use a real parser/serializer, not naive delimiter splitting. Cover quoted fields, delimiters inside quotes, embedded newlines, escaped quotes, BOM/encoding, line endings, empty fields, trailing empty columns where representable, and leading-zero identifiers such as `00123`. Prefer preservation over aggressive type inference; do not silently reinterpret strings that resemble numbers or dates.

Reserialization may normalize non-semantic byte details such as unnecessary quoting. “Preserve original format” means preserving CSV/TSV semantics and extension, not byte-for-byte identity.

If the user invokes a feature the original CSV/TSV cannot represent, do not silently lose it or silently convert. Warn and offer `Save as XLSX`.

### Goal 1 acceptance

Goal 1 requires same-format editable save for all approved Plain Text formats, intact XML safeguards, robust CSV/TSV import/export in Spreadsheets, an explicit XLSX-conversion choice for unsupported CSV/TSV features, and no regression in existing TXT/XML/XLS/XLSX workflows.

## Goal 2 — PowerPoint/PPTX fidelity

The supplied real PPTX shows a shared web/desktop rendering defect: PowerPoint renders a very large two-line first-slide title, while InkDOS renders the text substantially smaller and with different layout. Because web and desktop both reproduce it, investigate the shared Presentations importer/model/renderer rather than the Tauri wrapper.

Known evidence includes a 20 × 11.25 inch 16:9 slide, a title run at 112.5 pt, and negative OOXML character spacing `spc="-337"` (about -3.37 pt). The importer currently handles font size and common styling but the model/renderer does not represent character spacing. The renderer also uses a coherent point-based coordinate system (`EMU_PER_POINT = 12700`) for geometry and text.

Do **not** apply a blind font-only 4/3 conversion such as 112.5 pt → 150 CSS px. Scaling fonts independently of the point-based geometry can break proportions in otherwise correct presentations.

Required debugging path:

1. reproduce with the real PPTX;
2. inspect source OOXML;
3. inspect imported `PresentationModel` values;
4. inspect generated DOM/CSS;
5. measure actual textbox/font/wrapping behavior;
6. compare with the PowerPoint reference;
7. identify the narrowest proven root cause;
8. add a failing regression test where practical;
9. apply the minimum evidence-based fix;
10. rerun real and synthetic regressions;
11. verify existing presentation editing, round-trip and browser tests.

Where evidence confirms relevance, add character-spacing support through parse → model → renderer → preservation writer. Also verify textbox bounds, margins, line/paragraph spacing, wrapping, vertical alignment, soft hyphens, font fallback/metrics, placeholders, autofit, zoom transforms, clipping and line breaks. Do not fix unrelated fidelity behavior speculatively.

### Goal 2 acceptance

The real PPTX must have a reproducible regression path and documented root cause; title sizing/wrapping should materially align with the PowerPoint reference; relevant source formatting must survive model/rendering; no unjustified global scaling hack may be used; and the shared fix must benefit both web and desktop without breaking existing presentation behavior.

## Goal 3 — Desktop file integration and per-file windows

The installed experience should resemble traditional desktop Office behavior rather than browser tabs.

### One installation, workspace-specific entry points

Keep one InkDOS installation and one Tauri host. Where the OS permits, expose launch entries conceptually equivalent to:

- InkDOS
- InkDOS Documents
- InkDOS Spreadsheets
- InkDOS Presentations
- InkDOS PDF
- InkDOS Plain Text
- InkDOS EPUB

These may pass workspace arguments to the same executable/host. Windows Installed Apps should ideally show one InkDOS product, not six fake applications. Windows may expose Start-menu shortcuts, Linux may expose workspace-specific `.desktop` launchers, and macOS should remain one application bundle rather than six fake `/Applications` apps.

### One native window per file

Do not implement a central tab shell. Each opened file may have its own native InkDOS window. Two PPTX files should be able to coexist in two Presentations windows; a DOCX, PDF, etc. likewise get their own windows. Opening a second file from the same workspace must not replace the first solely because the workspace matches.

Reuse the same app-local importers/editors. Desktop routing should deliver the selected filesystem file into the existing workspace open path rather than create a parallel importer implementation.

### Strict associations and internal validation

Baseline mapping:

- Documents: `.doc`, `.docx`, `.rtf`
- Spreadsheets: `.xls`, `.xlsx`, `.csv`, `.tsv`
- Presentations: `.ppt`, `.pptx`
- PDF: `.pdf`
- EPUB: `.epub`
- Plain Text: `.txt`, `.xml`, `.md`, `.markdown`, `.json`, `.jsonl`, `.ndjson`, `.yaml`, `.yml`, `.log`, `.ini`, `.cfg`, `.conf`, `.toml`, `.properties`

OS associations are not enough. Each workspace must enforce its own allowlist. If an unsupported file reaches a workspace by drag/drop, command line, association mistake or other path, reject it with a clear `Unsupported file format` message. Do not silently redirect it to another workspace.

### Icons

Reuse **exactly** the existing workspace icons; do not create a new document-icon family for 2.3. DOC/DOCX/RTF use the existing Documents icon; spreadsheet formats use the existing Spreadsheets icon; PPT/PPTX use Presentations; PDF uses PDF; EPUB uses EPUB; text-family formats use Plain Text. Platform-specific installer/bundle/MIME plumbing may be required to expose these icons.

### Goal 3 acceptance

One installation, workspace-specific launch entries where appropriate, strict file associations and internal allowlists, one native window per opened file, multiple same-workspace files simultaneously, exact reuse of workspace icons, no silent rerouting, unchanged web Home, and platform-specific Windows/macOS/Linux behavior verified as far as CI and platform tooling permit.

## Goal 4 — Manual desktop updater

The updater is desktop-only. Web/GitHub Pages must not expose it or perform update checks.

### Privacy/network rule

No check on startup. No polling. No background update network activity. InkDOS makes no update-related request until the user explicitly selects `Check for updates`.

### Home control

Desktop Home gains only the previously approved small update/download control with tooltip `Check for updates`. Do not redesign Home, change the six workspace cards, or add an `Open file` card.

### UI states

Up to date:

> InkDOS 2.3.0  
> You're using the latest version.  
> OK

Update available:

> InkDOS 2.3.1 is available  
> Current version: 2.3.0  
> What's new  
> [concise user-facing release notes]  
> Cancel · Install

Release notes should come from the same update metadata response and preferably derive from the relevant `CHANGELOG.md` section, not raw commit messages.

Install should download the correct package, show useful progress, verify its signature, install from inside InkDOS, and avoid browser/GitHub/manual-installer handoffs. Verification failure must install nothing.

### Architecture

Prefer the official Tauri v2 updater plugin with signed updater artifacts, a committed/configured public verification key, private signing material held only in GitHub Actions secrets, and static HTTPS metadata such as `latest.json`. Do not build a custom security-sensitive updater or backend if the official mechanism satisfies the requirements.

Also provide an installed launch entry conceptually named `Check for InkDOS Updates`; it invokes the same updater flow and is not a second updater/service.

### Goal 4 acceptance

No automatic/background checking, web Home unchanged, desktop Home only gains the update control, latest/newer-version states are correct, notes are shown, signature verification is enforced, install occurs inside InkDOS, no normal browser/GitHub/manual installer path exists, private signing material is not committed, and the installed update entry invokes the same logic.

## Release definition

The combined result is **InkDOS 2.3.0**. Do not declare 2.3.0 complete merely because code exists. Completion requires all four goals in order, targeted regressions, repository/integrity checks, relevant browser tests, desktop build/package verification, platform integration review, updater metadata/artifact verification, `CHANGELOG` update, and a final requirement-by-requirement review against this specification.

## Development method and continuity

Use systematic debugging for defects, TDD for implementation changes where practical/required, and verification-before-completion before any success claim. Avoid speculative patches, no-op activity commits and unnecessary CI invalidation. Prefer targeted tests while developing and broad cross-browser/integrity gates at coherent merge/release checkpoints.

Automation may inspect state before this spec is approved, but runtime implementation must not begin until the user has explicitly reviewed and approved this written specification. After approval, development follows Goals 1 → 2 → 3 → 4 without reordering. Once 2.3.0 is released and the final four-goal review passes, development automations should stop making new product changes.

## Explicit non-goals

No web Home redesign; no `Open file` Home card; no central tabs; no one-file-per-workspace restriction; no six full installations; no Electron; no bundled Node desktop runtime; no automatic updater checks; no telemetry/backend; no silent conversion; no silent cross-workspace rerouting; no new document icon family; no unproven font-only global 4/3 PPTX scaling; no conversion of YAML/JSON/Markdown to TXT; and no automatic CSV/TSV-to-XLSX conversion merely because a file was edited.
