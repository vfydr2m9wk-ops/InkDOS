# InkDOS Unified Web and Desktop Release Design

## Goal

Make `main` the single canonical source tree for InkDOS across the web/PWA edition and installable Tauri desktop editions for Windows, macOS, and Linux. A single semantic version and Git tag must identify the same source commit for every distributed form.

## Canonical branch

`main` remains the canonical product branch. The existing browser/PWA source remains at the repository root. The Tauri host lives under `desktop/` and packages staged copies of the same root web assets; it does not fork or replace workspace engines.

The current `desktop-tauri` branch is the integration branch. It is merged into `main` only after the unified release workflow and repository contracts pass.

## Version model

`VERSION.json` is the human-readable product version source. Release tags use the exact form `vX.Y.Z` and must match `VERSION.json.version == X.Y.Z`.

The same version applies to:

- the browser/PWA edition;
- the Windows NSIS and MSI packages;
- the macOS app bundle and DMG;
- the Linux DEB, AppImage, and RPM packages.

Tauri configuration must be synchronized from `VERSION.json` during staging/build so a release cannot silently ship a desktop bundle with a different version.

## Tag release flow

A push of a tag matching `v*.*.*` from a commit reachable from `main` triggers the unified release workflow.

The workflow must:

1. check out the tagged commit;
2. validate that the tag version matches `VERSION.json`;
3. run the existing repository/static release contracts;
4. run the Tauri desktop contract and staging validation;
5. build Windows bundles on a Windows runner;
6. build macOS bundles on a macOS runner;
7. build Linux bundles on a Linux runner;
8. collect the native installers as workflow artifacts;
9. publish one GitHub Release using the tag;
10. attach every native installer to that release;
11. include the web URL in the release notes;
12. leave GitHub's source `.zip` and `.tar.gz` archives as the source distribution.

A normal push to `main` validates the web and desktop packaging contracts but does not create a public release.

## Web deployment

The web edition remains sourced from the same `main` tree and existing GitHub Pages deployment model. The release workflow does not create a second copy of the web application or a separate web branch. The release notes link to `https://vfydr2m9wk-ops.github.io/InkDOS/`.

If the Pages deployment workflow is already triggered by `main`, it remains authoritative. Tags identify released source; they do not create a separate Pages deployment lineage.

## Desktop packaging

Desktop packaging remains under `desktop/` and uses Tauri v2 with staged repository assets. Native binaries are build outputs only and must not be committed to the Git repository.

Expected release assets for x86-64 desktop runners are:

- Windows: NSIS `.exe` and WiX `.msi`;
- macOS: `.dmg` and, where useful for CI retention, `.app` bundle archives;
- Linux: `.deb`, `.AppImage`, and `.rpm`.

Architecture suffixes generated by Tauri are retained rather than renamed deceptively.

## Security and signing

The first unified release may contain unsigned development packages. The workflow must not invent signing credentials or weaken Tauri permissions. Windows signing and Apple signing/notarization remain separate hardening work that can be activated later through repository secrets.

## Failure behavior

The GitHub Release publication job runs only after validation and all three native platform builds succeed. A failed platform build must prevent creation of a partial public release.

Tag/version mismatch must fail before native builds begin. Existing tags are never force-moved by automation.

## Testing

Extend the desktop contract tests to verify:

- `main`-compatible workflow triggers exist;
- tag trigger uses `v*.*.*`;
- release publication waits for all native builds;
- workflow permissions include only the `contents: write` required for publishing release assets;
- tag and `VERSION.json` version validation exists;
- Tauri version synchronization exists;
- no generated installer is committed to the repository.

The existing browser regression and format-preservation suites remain authoritative for application behavior.

## Initial release

The repository currently declares InkDOS `2.1.0` in `VERSION.json`. If `v2.1.0` does not already exist, the first unified release tag is `v2.1.0` after the integration commit is on `main` and validation is green. If that tag already exists, automation must not overwrite it; a new semantic version is required instead.

## Success criteria

1. `main` contains both the unchanged web/PWA application and the Tauri packaging infrastructure.
2. `desktop-tauri` changes are integrated without creating a separate product fork.
3. A normal `main` push validates both web and desktop release contracts without publishing a release.
4. A `vX.Y.Z` tag whose version matches `VERSION.json` builds Windows, macOS, and Linux packages from the same commit.
5. One GitHub Release contains the native installers and links to the web edition.
6. Installer binaries are not stored in Git history.
7. Existing browser/PWA behavior and workspace ownership boundaries remain intact.
