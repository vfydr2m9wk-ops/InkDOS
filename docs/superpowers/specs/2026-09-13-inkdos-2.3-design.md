# InkDOS 2.3 Canonical Design Specification

**Status: USER-APPROVED**

Approval source: explicit user approval in the active InkDOS 2.3 development thread on 2026-09-12/13. In this workflow, the user's message `Aprovado` explicitly means to unlock the next gate while preserving the already-established order and checkpoint.

## Scope and fixed execution order

InkDOS 2.3 is executed in this order and must not be reordered:

1. Expand editable format coverage while preserving original formats where safe.
2. Diagnose and fix PPTX/PowerPoint fidelity using the supplied real regression plus focused synthetic tests.
3. Implement installed-desktop file associations, workspace-specific launch entries, strict format allowlists, and separate native windows per opened file while keeping one InkDOS installation/host.
4. Implement the manual-only desktop updater and its installed shortcut, with no startup/background checks and no Home redesign beyond the previously approved update control.

A later goal must not begin before the previous goal has a verified checkpoint.

## Goal 1 — editable format coverage

### Plain Text

Plain Text remains a raw-text editor. It supports at minimum:

- TXT
- XML
- MD / Markdown
- JSON
- JSONL / NDJSON
- YAML / YML
- LOG
- INI
- CFG
- CONF
- TOML
- PROPERTIES

Other text-only formats require explicit approval before being added.

For approved text formats, opening and saving preserves the original extension by default. The editor must not silently reinterpret a text format as an Office format.

### CSV / TSV

CSV and TSV belong to Spreadsheets, not Plain Text. They render as cells, remain editable, and save back to CSV/TSV by default.

Parsing and serialization must correctly preserve or handle:

- quoted fields
- embedded delimiters
- embedded newlines
- BOM/encoding behavior
- leading-zero strings

If the user invokes a spreadsheet feature that the original CSV/TSV format cannot represent, InkDOS warns the user and offers conversion to XLSX. It must never silently convert.

## Goal 2 — PPTX fidelity

Use the supplied real-world PowerPoint regression as the primary reproduction. Add focused synthetic regressions that isolate each identified failure mode. Follow systematic debugging: reproduce, trace root cause, compare with working patterns, state a single hypothesis, test minimally, and only then implement a fix. Preserve unrelated presentation behavior.

## Goal 3 — desktop associations and native launch model

The installed desktop build must:

- associate supported file types with the correct workspace;
- expose workspace-specific launch entries using the existing workspace icons exactly;
- enforce strict per-workspace extension allowlists;
- reject unsupported extensions with a clear notification rather than redirecting;
- open each file in a separate native window;
- retain a single InkDOS installation and host, not six installations or duplicated full executables;
- avoid introducing a central tab system.

## Goal 4 — manual-only updater

The installed desktop build may access the network only for the updater, and only after explicit user action.

Requirements:

- no startup update check;
- no background polling/checks;
- no automatic update download/install without explicit user action;
- retain the previously approved Home update control without otherwise redesigning web Home;
- provide the installed updater shortcut/control;
- compare installed version with the published latest version only when invoked;
- show update availability and release/change notes;
- permit explicit Install or Cancel;
- when already current, report that the installed version is the latest version.

## Global restrictions

- Web Home remains visually unchanged except for the previously approved update control.
- No central tab system.
- No six separate installations or full duplicate executables.
- Existing workspace icons are reused exactly for file associations and launchers.
- Each workspace rejects unsupported extensions clearly instead of redirecting.
- Preserve local-first behavior.
- No telemetry.
- No backend.
- The updater is the only approved network path, and only after explicit user action.
- Do not work on Lewis translation, Global Blue, or unrelated projects.

## Development discipline

- Refetch current `main`, open PRs, and CI before runtime/code mutation.
- Use TDD: targeted failing test first, observe RED, minimal implementation, observe GREEN.
- Use systematic debugging for defects, especially PPTX fidelity regressions.
- Run targeted tests before broader repository/cross-platform verification.
- Record exact SHAs, tests, and blockers at checkpoints.
- Use verification-before-completion before claiming any goal or release complete.

## Release-complete condition

InkDOS 2.3 is release-complete only when all four goals satisfy their acceptance criteria, repository and cross-platform tests are green, release artifacts and updater metadata are verified, and a final review of all four goals is complete. At that point, record the release-complete checkpoint and stop making new changes.
