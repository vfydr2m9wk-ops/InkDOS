# InkDOS 2.4.0 -> 2.4.3 upgrade validation plan

Status: release-gate plan. This document does not authorize publication.

## Repository-verifiable prerequisites

- The 2.4.3 candidate commit is on `main` and all active 2.4.3 P1/P2 review threads are resolved by tested code or explicitly invalidated with evidence.
- Persistent CI on both pull requests and `main` runs the clean-snapshot release validation plus the Documents 2.4.3 interaction browser regression, Home Windows-scale browser harness, Spreadsheets 2.4.3 fill/clear browser regression, and staged desktop runtime check.
- `VERSION.json`, `desktop/src-tauri/tauri.conf.json`, and `desktop/src-tauri/Cargo.toml` all declare 2.4.3 before the release tag is created.
- `desktop/scripts/release_version.py --check-config`, `scripts/run_release_validation.py`, Goal 4 updater contracts, desktop contracts, and `desktop/scripts/stage_web.py --check` pass on the exact candidate head.
- The tag-only release workflow remains fail-closed: tag must be exactly `v2.4.3`, belong to `main`, signing key/public key must be present, artifacts must come from the same run, and immutable provenance must match the tagged commit.
- Updater artifacts remain exactly one Windows NSIS `.exe` plus `.exe.sig`, one macOS `.app.tar.gz` plus signature, and one Linux `.AppImage` plus signature. `latest.json` must bind URLs to `v2.4.3` and embed non-empty signatures. It must not be made public before all gates below pass.
- Prior public releases and their tags/assets are immutable; the 2.4.3 process must not overwrite them.

## Real Windows/device validation

Use a disposable or backed-up Windows installation with the public InkDOS 2.4.0 installer. Preserve representative user documents outside the application installation directory and record hashes/copies before the test.

1. Install and launch public 2.4.0. Confirm its displayed version and baseline opening/saving of representative Documents and Spreadsheets files.
2. Configure the test to consume the staged/draft 2.4.3 updater metadata and signed Windows updater artifact without making 2.4.3 the public `latest.json`.
3. Trigger the in-app updater. Verify signature acceptance, download, passive NSIS install, process restart/launch, and resulting application version 2.4.3.
4. Confirm user documents and unrelated user files are byte-identical unless the tester explicitly edits them. Confirm no migration rewrites document content merely by launching/updating.
5. Re-open the baseline files and exercise the 2.4.3 Documents, Home, and Spreadsheets regression scenarios on Windows/WebView2, including 100%, 125%, and 150% display scaling and touch/pen fill behavior when suitable hardware is available.
6. Reboot once and verify InkDOS launches normally, file associations/workspace launchers remain functional, and updater state does not repeatedly offer 2.4.3.
7. Record Windows version, WebView2 version, installer/updater artifact filename, SHA-256, signature verification result, source 2.4.0 build, destination 2.4.3 commit/tag candidate, and pass/fail evidence.

## Publication gate

The preferred path is to complete the real Windows/device upgrade test before publication. For InkDOS 2.4.3, the pre-publication Windows/WebView2 2.4.0 -> 2.4.3 updater validation has been explicitly waived by the user. This waiver does **not** count as a Windows validation pass and must remain recorded in `config/release-authorization.json`; post-launch updater validation remains required.

Publication may proceed only after the repository-verifiable prerequisites pass and either (a) structured Windows/device evidence validates the exact release bundle, or (b) an explicit user-authorized waiver is recorded with no fabricated evidence. In either case, explicit user publication authorization is required.
